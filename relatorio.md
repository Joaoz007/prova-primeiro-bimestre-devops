## 3. Arquitetura AWS, segurança e AWS Academy Learner Lab

A arquitetura AWS foi criada utilizando Terraform na região `us-east-1`, conforme solicitado na prova. A solução possui uma VPC com CIDR `10.0.0.0/16`, uma subnet pública para a EC2 e duas subnets privadas em zonas de disponibilidade distintas para o RDS subnet group. A EC2 utiliza uma instância `t2.micro` e o RDS utiliza PostgreSQL em uma instância `db.t3.micro`. O RDS foi configurado como privado, com `publicly_accessible=false`, armazenamento criptografado e `multi_az=false`. As duas subnets privadas são utilizadas no DB subnet group, sem transformar o RDS em uma configuração Multi-AZ. A EC2 utiliza o `LabInstanceProfile` disponibilizado pelo AWS Academy, sem criação de usuários, grupos ou roles IAM adicionais. Nos Security Groups, a EC2 possui acesso às portas necessárias para SSH e para a API, enquanto o RDS aceita a porta 5432 somente a partir do Security Group da EC2. O estado do Terraform foi configurado em S3 com versionamento e criptografia, utilizando DynamoDB para locking. A senha do banco não foi armazenada no código-fonte ou em arquivos versionados. Durante o deploy, a API foi executada em Docker na EC2 e conseguiu acessar o RDS privado através da configuração de rede e dos Security Groups.

## 4. Validação, testes e responsabilidade

A validação foi realizada em diferentes etapas, tanto no ambiente local quanto na AWS. Primeiro, a aplicação foi executada com Docker Compose e testada contra o PostgreSQL local. Depois, a infraestrutura AWS foi criada com Terraform e a API foi executada em um container Docker na EC2. O endpoint `/health` retornou `{"status":"ok"}`, confirmando que a aplicação estava funcionando. Em seguida, foi realizado o teste completo do CRUD em produção. O `POST /reservas` criou uma reserva com sucesso e retornou o identificador `1`. O `GET /reservas` recuperou a reserva persistida no banco e o `GET /reservas/1` confirmou a consulta por identificador. O `PUT /reservas/1` alterou o status da reserva para `confirmada`. Por fim, o `DELETE /reservas/1` retornou HTTP 204. Durante o processo também ocorreu um erro de conexão com o RDS por ausência de SSL, que foi identificado pela mensagem do PostgreSQL e corrigido na configuração do cliente `pg`. Outro erro ocorreu quando uma marcação de bloco de código foi inserida acidentalmente no arquivo JavaScript, sendo identificado pelo erro do Node e corrigido antes do novo teste. A responsabilidade pela validação foi minha: os comandos foram executados e os resultados analisados antes de considerar cada etapa concluída. As evidências foram registradas no diretório `evidencias`, incluindo Docker, Compose, Terraform Plan e validação da API na AWS.
